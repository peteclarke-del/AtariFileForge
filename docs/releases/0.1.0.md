# Atari File Forge 0.1.0

The first usable release. Atari File Forge opens, edits and saves the disks and
drives of the whole ST range, from a single-sided 520ST floppy to a partitioned
Falcon030 IDE drive, prepares a drive so it boots, and starts any of them in
Hatari with the machine the work is meant for.

It runs as a Docker service reached from a browser, and as a native Linux
desktop application built with GTK 4. Both share one workbench, and a Debian
13 or Ubuntu 24.04 package is published for AMD64, ARM64 and ARMv7.

## What it does

**Disks and drives.** ST sector images at every geometry from 360 KiB to
1.44 MiB, MSA and DIM containers, Pasti STX captures read-only with a
per-track protection report, and HFE and SCP flux containers through the
bundled HxCFloppyEmulator converter. Hard drives with AHDI, ICD or PC partition
tables, including byte-swapped images dumped through an IDE adapter. GEMDOS is
read and written with its 8.3 names, attribute byte and datestamps intact, and
the TOS release limits for a partition's size are reported rather than
discovered.

**Preparing a drive.** Partitioning, formatting and the boot sector, then a
hard-disk driver from your own copy or driverless booting under EmuTOS, the
folders a prepared drive expects and a desktop configuration. A replacement
desktop can go on at the same time. NeoDesk and Geneva are set up the way
Gribnif's own installers set them up: the JARxxx cookie jar first in `AUTO`,
and Geneva's `GEM.CNF` told to start NeoDesk as its desktop, so a prepared
drive comes up in Geneva with NeoDesk running. A floppy can be staged onto a
drive, installed into its own folder, or run through its own installer under
the emulator.

**The emulator.** Hatari for every machine in the range, over floppy, ACSI,
SCSI, IDE and host-folder media. A hard drive is attached whole to the
interface the hardware profile declares and booted from; "Mount only" attaches
it without starting it. A TOS ROM you supply is preferred, and the bundled
EmuTOS 1.4 boots the machine when none is found.

**Hardware profiles.** Twelve presets and six base machines, each built from
add-ons with their requirements and conflicts. Applying a profile applies it to
the whole workspace, and every preset is held by a test to the same rules the
server uses, so a preset can no longer carry hardware its machine cannot take.

**ROMs.** TOS and cartridge ROM decoding: the header, both dates, the country
and video standard, trap entry points proven from their vector installs, and
the cartridge application chain. Cartridge ROMs can be built and split into the
chip files a real board takes.

**Editors and analysis.** GFA BASIC 3 and Atari ST BASIC are read and written,
STOS BASIC is read, and 68000-family disassembly is annotated with the TRAP
calls, TOS system variables and ST hardware registers. The health dashboard,
the manifest and the README inside every saved package report the `AUTO`
order, desktop configuration, program headers, boot evidence, name conflicts
and TOS limits.

**Deployment.** Packages for a Gotek, an SD card, a CF card, a host folder and
a real ACSI drive, each with its own verification steps.

## Upgrading from a development build

- **Drives prepared before this release** with a driver whose distribution
  carries no loader may have a root sector marked bootable with nothing in it.
  A real TOS ROM halts on that with a double bus error before the desktop
  appears. Prepare the drive again and the mark comes off.
- **Drives with NeoDesk or Geneva** prepared before this release lack the
  cookie jar, and Geneva stops at boot with "You must run JARxxx before
  Geneva". Prepare the drive again with the same desktops ticked. Programs
  already in `AUTO` and accessories already in the root are kept as they are.
- **Saved hardware profiles** are corrected on first use. Only the entries that
  were invalid for their machine are removed, so any other edit you made to a
  preset is kept.
- **Undo** no longer reverses a rename or a profile change, neither of which
  touches the image's contents, and the Undo dialog names the change it will
  reverse. A development build copied the whole image into an undo point each
  time a profile was applied. Those copies can be deleted in **Edit →
  Checkpoints**, and a copy left half-written by closing the application is now
  removed automatically.

## Known restrictions

The [product handbook](../../README.md#known-limits-of-this-release) lists these
in full. In short:

- The Online Library's search and download workflow is not finished.
- ST picture, music and resource formats are not previewed.
- The ST character set's glyphs below code 32 are not yet drawn in filenames.
- The 1.44 MiB flux round trip has not been measured on hardware.
- AHDI and ICD Pro carry no root-sector loader this application can write. Run
  the driver's own installer once, or boot the drive driverless under EmuTOS.
- No TOS ROM is shipped. EmuTOS boots every machine without one.
- The real-hardware gate has not been recorded for this release. Keep a
  known-good copy of anything you put onto a real machine.

## Validation

The Python, JavaScript and browser suites and the AMD64, ARM64 and ARMv7 image
builds run on every commit, and the release workflow built and inspected the
six packages attached to this release before publishing it. The
[release checklist](../RELEASE-CHECKLIST.md) defines the full gate.
