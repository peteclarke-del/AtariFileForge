# Atari File Forge 0.3.0

A drive prepared here now boots on a machine running its original TOS ROM.
Until this release, preparing a drive with AHDI or ICD Pro installed the driver
file but not the loaders that start it, and wrote a desktop configuration that
TOS 1.x never reads. A Mega ST running TOS 1.04 therefore saw no hard disk at
all, and once the loaders were added by hand, the desktop still ignored
everything that had been installed on it.

## Loaders copied from a prepared drive

A genuine ROM finds a hard-disk driver through two loaders: one in the drive's
root sector, which reads the boot partition's boot sector, and one in that boot
sector, which reads the driver file it names. AHDI and ICD Pro keep both inside
their own Atari installation programs rather than as files, so there was
nothing here to write, and the preparation said so.

The Prepare dialog now has a **Boot loader** choice. Open a drive the driver
has already prepared in the other pane, choose it there, and both loaders are
copied onto the drive being prepared:

- the root sector's loader, below the partition table, while the table itself,
  the drive size and the bad-sector list stay this drive's own;
- the boot sector's loader and the name of the file it loads, while the serial
  number and the BIOS parameter block stay this partition's own.

Both checksums are recomputed so that each sector sums to `0x1234`. The driver
file is written under the name the copied loader asks for, `ICDBOOT.SYS` for
ICD, and the partition being prepared is flagged as the one to boot, with the
flag cleared from every other. A drive partitioned here has no partition
flagged, so without that last step the copied loaders would run and then boot
nothing. The other drive is only read.

The copy is refused rather than made when it could not work: when either of the
other drive's sectors is not one the ROM executes, and when its boot sector
loads a different driver's file from the one chosen. A partition further down
an XGM chain has no root-sector entry to flag, and preparing one says so.

A drive partitioned and prepared this way with ICD Pro 6.55A, its loaders
copied from a drive ICD itself prepared, boots in Hatari as a Mega ST with
genuine TOS 1.04: ICD's Auto-Boot finds all four partitions and starts from C:.

## A desktop configuration TOS 1.x reads

TOS 1.x reads `DESKTOP.INF` and nothing else, while TOS 2.05 and later read
`NEWDESK.INF` first. Preparation always wrote `NEWDESK.INF`, so on a TOS 1.x
machine an installed program, or a replacement desktop, was simply not there.

The file a drive is given now follows its hardware profile. A TOS 1.x release,
or an ST or Mega ST that names no release, gets `DESKTOP.INF`. Everything else
gets `NEWDESK.INF`, as before. `DESKTOP.INF` is written in TOS 1.x's own
spelling, with no `#K`, `#N`, `#Y` or `#X` records, because that desktop stops
reading at a record it does not know.

Installing a program writes its record into the file the drive's TOS reads.
When the drive also carries the other spelling, that file learns the program
too, so a drive moved between a TOS 1 and a TOS 2 machine shows it on either.
TOS 1.x cannot put a program's icon on the desktop itself, so there it is
installed as an application and you are told to open its folder.

## Known restrictions

The [product handbook](../../README.md#known-limits-of-this-release) lists the
known limits. The loaders are copied rather than written from scratch, so a
drive the driver has already prepared has to be at hand. The real-hardware gate
has not been recorded for this release; keep a known-good copy of anything you
put onto a real machine.

## Validation

The Python, JavaScript and browser suites and the AMD64, ARM64 and ARMv7 image
builds run on every commit. The release workflow builds and inspects the six
packages attached to this release before publishing it: EmuTOS present, no TOS
ROM, and the bundled HxCFloppyEmulator converter running. The
[release checklist](../RELEASE-CHECKLIST.md) defines the full gate.
